# LLM Summary Evaluator

## Purpose

Use this skill when you need to audit the quality of Kapyn's AI-generated summaries — either spot-checking individual items or running a batch review after a pipeline change. It applies the **G-Eval / LLM-as-judge** pattern: a structured prompt asks the judge model to score each dimension independently and explain its reasoning.

Trigger phrases: "check this summary", "evaluate these summaries", "is this summary good?", "audit the pipeline output", "why does this summary look wrong?"

---

## Key concepts

### G-Eval (LLM-as-judge with chain-of-thought)

G-Eval decomposes evaluation into explicit sub-criteria before scoring. The judge first generates evaluation steps, then applies them. This forced decomposition:
- Reduces scoring randomness
- Surfaces specific failure modes instead of a vague number
- Achieves ~85% agreement with human raters

**Three evaluation dimensions for Kapyn:**

| Dimension | What it measures | Passing threshold |
|---|---|---|
| **Accuracy** | Factual fidelity to source — no hallucinated claims, no omitted key facts | ≥ 4/5 |
| **Tone** | Matches Kapyn voice — calm, minimal, no hype, no marketing language, no emojis | ≥ 4/5 |
| **Length** | 40–80 words, readable in ~30 seconds | Pass/Fail |

### Known judge biases to guard against

- **Verbosity bias:** longer summaries score higher even if bloated — penalise explicitly
- **Self-enhancement bias:** if using the same model that generated the summary, it may favour its own output — prefer a different judge model or add adversarial prompting
- **Positional bias:** irrelevant in single-item evaluation, but shuffle order in batch runs

## Application

### Step 1 — Assemble the evaluation input

For each summary to evaluate, gather:
```
SOURCE_TITLE: <original article headline>
SOURCE_CONTENT: <first 1500 words of article, or full if short>
GENERATED_SUMMARY: <Kapyn summary text>
```

### Step 2 — Run the judge prompt

Use this prompt with Claude (Sonnet or Opus) or Gemini Flash as judge:

```
You are evaluating a news summary generated by an AI content pipeline.
Score the summary on THREE dimensions. For each dimension:
1. List the evaluation steps you will apply
2. Apply them
3. Give a score 1-5 and a one-sentence finding

---
DIMENSION 1 — ACCURACY (factual fidelity to source)
Evaluation steps:
- Check every factual claim in the summary against the source
- Flag any claim not supported by the source (hallucination)
- Flag any omitted critical fact that changes meaning

DIMENSION 2 — TONE (matches Kapyn voice)
Evaluation steps:
- Check for marketing/hype language ("revolutionary", "game-changing", "incredible")
- Check for emojis
- Check for exclamation marks
- Check for passive voice or weak hedging ("it seems", "reportedly may have")
- Check that it reads like a smart friend explaining, not a press release

DIMENSION 3 — LENGTH (40-80 words, ~30-second readability)
Evaluation steps:
- Count words
- Flag if under 40 (too thin) or over 80 (too long)

---
SOURCE_TITLE: {title}
SOURCE_CONTENT: {content}
GENERATED_SUMMARY: {summary}

---
Respond in EXACTLY this format:

ACCURACY_SCORE: <1-5>
ACCURACY_FINDING: <one sentence>

TONE_SCORE: <1-5>
TONE_FINDING: <one sentence>

LENGTH_SCORE: PASS | FAIL
LENGTH_FINDING: <word count and verdict>

OVERALL: PASS | REVIEW | REJECT
OVERALL_REASON: <one sentence — if REJECT, say exactly what to fix>
```

### Step 3 — Interpret results

| Result | Action |
|---|---|
| All PASS, scores ≥ 4 | Ship — no action needed |
| REVIEW | Human editor should check before next fetch cycle |
| REJECT | Delete from `news_items` and optionally re-run `classifyAndSummarize` |
| Accuracy < 3 | Delete immediately — factual errors are brand-damaging |

### Step 4 — Batch evaluation (pipeline audit)

To audit recent ingestion output:

```sql
-- Pull the last 50 items for review
SELECT id, title, summary, source_url, created_at
FROM news_items
ORDER BY created_at DESC
LIMIT 50;
```

Run each row through the judge prompt. Flag items with OVERALL = REJECT for deletion via:
```sql
DELETE FROM news_items WHERE id IN (<flagged_ids>);
```

## Examples

### Good summary (PASS)

```
SOURCE: "Anthropic releases Claude 3.7 Sonnet with extended thinking mode"
SUMMARY: "Claude 3.7 Sonnet is Anthropic's latest model, adding an extended thinking mode that lets it reason through complex problems before responding. The model shows a 30% improvement on MMLU and coding benchmarks. Available now via API with thinking tokens billed separately."
```

- Accuracy: 5/5 — all claims traceable to source
- Tone: 5/5 — no hype, active voice, clear first sentence
- Length: PASS — 52 words

### Bad summary (REJECT — tone failure)

```
SUMMARY: "Anthropic just dropped an absolutely revolutionary new AI that will completely change how developers work!! Claude 3.7 is incredible and a massive leap forward 🚀"
```

- Accuracy: may be fine but irrelevant
- Tone: 1/5 — "revolutionary", "incredible", "absolutely", "completely change", "!!", emoji
- Length: FAIL — 33 words

### Bad summary (REJECT — accuracy failure)

```
SOURCE: "Meta releases Llama 4 with 128K context"
SUMMARY: "Meta releases Llama 4 with 256K context window and multilingual support for 20 languages."
```

- Accuracy: 2/5 — hallucinated "256K" (source says 128K) and "20 languages" (not mentioned)

## Common pitfalls

- **Don't use the same model that generated the summary as the judge** — self-enhancement bias inflates scores
- **Don't evaluate without the source** — tone and length alone are insufficient; accuracy requires the source
- **Don't batch more than 10 items per judge call** — quality degrades; run per-item
- **Don't treat LENGTH as a hard gate alone** — a 38-word summary that is accurate and well-toned is better than a padded 60-word one
- **Do run evaluation after any prompt change** to `buildClassifyAndSummarizePrompt` in `api/news/fetch/route.ts`
