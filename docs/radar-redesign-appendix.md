# Kapyn Radar — Reference Pattern Library

A buildable brief. The unifying thesis across all six references: **keep the #0a0a0a canvas; inject color through content (logos, imagery, accent tiles), not chrome; make a FEW things huge.** This resolves the founder's tension — "more colorful + higher contrast" yet still "calm" — because calm = restrained chrome + black breathing room, while colorful = the few content objects are vivid.

---

## 1. Imagery

- **Logo-as-color-anchor on every row/tile/card** *(App Store, Product Hunt Now, Spotify)* — Render the tool/model/agent's real brand logo as a 48–56px rounded-square (radius ~12px) leading element on every list row and tile. This is the single highest-leverage fix for "too dark/text-heavy": a vertical ribbon of distinct brand logos makes the screen colorful while chrome stays near-black. Pull from favicon/og-image at ingest and cache. **Rule (from Spotify): never render a list row without a logo on the left.** Fallback: a category-accent-tinted monogram tile so the grid never goes flat.
- **Full-bleed image hero with title BELOW, never overlaid** *(Perplexity, Product Hunt Stories)* — The lead image is edge-to-edge ~16:9 (or ~50% viewport); the headline sits in a clean text block beneath it on #0a0a0a. No scrims, no contrast fights — the image carries color, the type stays crisp. Use the tool's product shot / brand gradient / logo art. Each card looks distinct (violet LLM vs orange OSS) without touching the shell.
- **On-image provenance watermark** *(Perplexity)* — Burn a small low-opacity maker logo / "Verified" mark into the hero image's bottom-right. For a discovery surface this doubles as the trust signal ("is this real, who makes it") while keeping the text block below uncluttered.

## 2. Color

- **Color from CONTENT, not CHROME** *(all six — and the explicit anti-pattern in MCP Market)* — Keep #0a0a0a body / #111 card surface / quiet monochrome nav and dividers. All saturation enters through: real logos, full-bleed imagery, per-category accent tiles, filled pills. **MCP Market is the failure mode to reject**: it uses color in exactly two faint spots on gray-on-near-black — borrow its IA, reject its skin.
- **Per-category accent as taxonomy, not decoration** *(Product Hunt Search, Spotify, MCP fix)* — Use Kapyn's existing 9 accents as meaningful color: violet=AI/models, blue=dev-tools, orange=open-source, green=startups, cyan=research, amber=funding, indigo=big-tech, teal=infra, purple=policy. Apply them in **high-information spots only**: filled category pills, solid-color tiles, monogram fallbacks, hero gradients, badges. Never as full row/panel backgrounds.
- **Color-as-state / color-as-reward** *(Spotify, Product Hunt onboarding)* — The screen stays neutral until you engage, then blooms. Active filter pill = saturated fill (tinted to its own accent); selected multi-select row = accent check; the "Track" pill = solid vs "Tracking" = ghost. Engaging the feed makes Kapyn's palette bloom.
- **Gold #E8B25C reserved for chrome/active-state only** *(Product Hunt Now/Stories, Perplexity, onboarding)* — One accent used surgically: active tab underline, the single FAB, the live/dynamic token only (the date in "RISING · Jun 18"), the arrival CTA. Never on body chrome, never the only color on screen.
- **One saturated chrome element max per screen** *(Product Hunt Now)* — If Radar needs a primary action (Track / Ask), express it as a single gold circular FAB bottom-right. Its loudness is earned by being solitary; a second colored chrome control breaks the discipline.
- **Frosted scrim where image meets text** *(App Store)* — If any text must sit over imagery, fade a gradient scrim from image-color down to card surface so the headline stays legible. (Default preference: put title below the image instead.)

## 3. Typography / Prominence

- **4-tier type scale — the structural fix for flatness** *(Product Hunt onboarding, App Store, Spotify, MCP)* — Adopt wholesale:
  - **Headline / hero** — Space Grotesk, 28–34px bold, warm-white #E8E4DE (single loudest element)
  - **Tiny caps eyebrow** — ~11px, letter-spaced, muted or accent-tinted ("NEW MODEL", "RISING", "FOR BUILDERS")
  - **Row/card name** — ~16–22px bold warm-white
  - **Muted one-liner** — ~14–15px #737373, two-line clamped
- **Prominence by SIZE GAP, not by color shouting** *(App Store, Spotify, onboarding)* — The 2.5–3:1 leap from eyebrow → headline is the whole effect. This is how Radar gets "bigger fonts + a few very prominent things" without hype: one element huge, everything else small and quiet.
- **Editorial headline framing, not just the name** *(App Store)* — Hero headline = a benefit line ("Ship code faster with Cursor"), not the bare tool name. Eyebrow carries the curation reason; sub carries one calm line of context.
- **Two-tone warm display headline** *(MCP fix)* — Keep the two-tone trick ("On the [Radar]") but in warm tones — #E8E4DE key word, #737373 framing word — in Space Grotesk, NOT monospace. Monospace stays only for version/code strings.
- **Strict two-line clamp, overflow deferred to tap** *(Perplexity, Product Hunt Now)* — Name + one 2-line-clamped descriptor, then inline "More" expands the detail sheet. The clamp enforces uniform row height so the logo ribbon and right-rail metric stay aligned — density that still feels calm.

## 4. Structure — cards / tiles / rails / grids

- **Two densities for two intents** *(Perplexity + Product Hunt Stories + MCP)*:
  - **Today = image-led, one-thing-per-fold.** A single hero owns the viewport; the next card's image peeks at the bottom to pull the swipe (mirrors Kapyn's swipe DNA). Limit to one hero + one secondary card before scroll.
  - **Browse = 2-column tile grid** at 430px (MCP's 3-up is desktop). Equal-height tiles scanned as a gallery; each tile leads with logo on an accent-tinted card + name + one-liner.
- **Named editorial rails as the Today spine** *(MCP IA, App Store, Product Hunt, onboarding eyebrows)* — Stack of titled sections, each a different SHAPE so the eye gets rhythm (Spotify's key move — Radar is flat today because it repeats one card type): "Official" (verified vendors, real logos) → "On the Radar" (editor's picks) → "Top this week" (signal-ranked) → "Just landed" (newest). Header = warm-white bold ~18–22px LEFT + quiet "See all" affordance RIGHT.
- **Solid-color tile rail** *(Spotify — the direct antidote to flat/dark)* — A horizontal rail of ~160px flat saturated tiles, each tinted to its category accent, with the real logo floating on the color and the NAME bold ~22px overlaid bottom-left, tiny caps eyebrow top-right ("MODEL"/"AGENT"/"MCP"). Flat solid blocks, not gradients — reads instantly, avoids the hyped look. Use 2–3 rails max to stay calm.
- **Anchored action row at card base** *(App Store)* — End each hero with: logo + bold name + 2-line one-liner + right-aligned filled pill CTA ("View" / "Add to Toolkit"). The pill is the one bright tappable thing; the eye sweeps hero-art → headline → pill.
- **Standardized right-edge pill column** *(App Store, Product Hunt onboarding)* — One pill component, right-aligned on every row, binary weight: solid accent fill = act ("Track"), ghost outline = done ("Tracking"). Creates a consistent right-edge scan column; a glance down the list shows what still needs action. Optional microcopy beneath ("Free", "Open source", "API").
- **Minimal top bar** *(Spotify)* — Top-left: a single circular lens/identity dot (tinted to active lens). Then the lens pills. Nothing else — push bold headers and color rails into the scroll. Protects the 430px width. *(All overlays/sheets portal to #phone-overlay-root, position: absolute — per Kapyn rules.)*

## 5. Curation / Browse

- **Tiny-caps curation eyebrows** *(onboarding, App Store, MCP)* — "NEW THIS WEEK", "RISING", "FOUNDERS ARE TRACKING", "FOR BUILDERS" above each rail. Near-zero ink, gives the hand-tended editorial feel for free.
- **Section title + chevron / "See all"** *(App Store, MCP)* — Bold title LEFT + quiet colored "See all →" RIGHT; each tier expands into a full Browse view. Establishes importance + escape hatch without heavy headers.
- **Filled saturated category pills as navigation** *(Product Hunt Search)* — Render the 9 category filters as FULLY FILLED accent-color pills (violet/blue/orange/…) with bold warm-white text and a chevron-in-circle, not gold-outline chips. The palette IS the navigation — you recognize a category by hue before reading. "See all" top-right.
- **Time/recency browse axis** *(Product Hunt "Time travel")* — A second entry into the catalog: "Today / This week / This month / All-time" rows, each with a colored circular gradient icon + muted dek. Pairs naturally with Kapyn's 48h freshness model (Today = live window; longer periods = curated retrospectives).
- **Curation descriptor under each section header** *(Product Hunt Stories)* — A muted line naming the curation source ("Picked for builders this week", "Trending in your stack") so the surface feels editorial, not algorithmically dumped — earns trust.
- **Verification badge** *(MCP, Product Hunt Featured)* — A single restrained chip on first-party vendor entries only: accent at ~15% bg + light accent text (e.g. #1a0533 bg / #c4b5fd text for ai-models). The loudest thing on a verified card, silent everywhere else.
- **Search-first entry** *(MCP)* — A persistent warm filled search input near the top ("Find a tool, model, or agent…") on #111 with a colored glyph — seeds the "Ask Kapyn" RAG roadmap. Search-first + curated-tiers-below = the navigate-OR-browse duality.

## 6. Metrics

- **Exactly ONE right-aligned signal metric per row** *(Product Hunt Now/Discussions)* — One number under a small spark/up-triangle glyph, list ranked descending. No competing timestamps or secondary stats. For tools: "saves this week" / "launches tracked" / a "Radar score". The lens system re-ranks by swapping which metric drives the sort — same layout, different signal.
- **One live count per category card as proof-of-depth** *(MCP)* — Each Browse card = colored accent icon + name + a formatted count ("142 tools", "38 models"), sorted descending so the grid self-ranks (important categories land top-left). The count makes the catalog feel alive and large.
- **Demote secondary metadata by hairline + muted grey** *(Perplexity)* — A thin utility strip under each card: recency ("New" / "Updated 2d ago") left; Save / Share / overflow right, low-contrast. Never competes with the logo + name.

## 7. Onboarding / Personalization

- **Stepped bottom-sheet, one huge headline per step** *(Product Hunt onboarding)* — First-run lens picker = a sheet over a blurred Today feed: "1 of 2" counter + X, one giant ~28px warm-white headline ("What are you here to do?"), one muted line, then the three lenses (Builder / Founder / Exploring) as a quiet ~56px-row list with hairline dividers. One idea per screen; prominence from size, not decoration. *(Reuse this sheet pattern for any Radar modal.)*
- **Selection = accent circle on the right edge** *(Product Hunt onboarding)* — Hollow outline = unselected; solid accent fill + white check = selected. On the category multi-select ("Pick the spaces you track"), each check lights up in THAT category's accent — the screen blooms into Kapyn's rainbow only as you engage.
- **Single bottom-docked CTA that names the payoff, with escalating saturation** *(Product Hunt onboarding)* — Full-width, ~16px bold, label names the destination ("Next: Tune your Radar" → "Show my Radar"), never generic "Next". Neutral/outline early steps → gold #E8B25C fill on the final tap so arrival feels earned.
- **Lens system as the visible spine** *(Perplexity tabs, Spotify pills)* — Run the lenses as a horizontal pill/tab row at the top of Today — "For You / Builder / Founder / Exploring" — active in gold (or tinted to its own accent: Builder=blue, Founder=amber, Exploring=cyan), siblings muted, bleeding off-right to invite scroll. Selecting a lens re-tailors the hero deck below, exactly as Perplexity's tabs re-tailor the feed. Makes personalization a visible spine, not a hidden setting; it also re-selects WHICH single hero leads, so the same calm layout feels personalized.
- **Inline "Tune your Radar" taste-signal card** *(Perplexity)* — Between hero cards: "Tap a category once to see more, twice to mute it" + a band of colorful per-category accent chips. This is a deliberate color moment AND cheap personalization with no auth-gated settings screen.
- **2-tab "Curated vs For You" toggle + unread dot** *(Product Hunt)* — Lightweight text toggle inside Today (active bold + short gold underline, inactive grey) with an unread dot when new tools matched your lens since last visit. Cheap retention hook ("new for your lens"); keeps the bottom nav intact.
- **Low-commitment escape valves** *(Product Hunt onboarding)* — A quiet "✨ Surprise me / Randomize" link at section headers to re-roll suggestions; step counter + X always present. Bold flow never feels forced.

# RADAR VISUAL DIRECTION — Unified Brief

The single identity, distilled: **Warm near-black canvas. One loud image-led hero per screen, then a colorful, scannable field where every Thing wears its category's color (and, where possible, its real logo). Big warm-white display type anchors each section. Dead monochrome gray is eliminated. Motion stays deliberately quiet.** Loud surfaces, quiet motion. Color and contrast carry the energy; restraint in density, copy, and motion keeps it calm.

All six diagnoses converge on the same root cause and the same keystone fix, so the brief is unusually low-conflict. The disagreements are about *magnitude* (exact px, exact hue lightness, image-everywhere vs. image-where-earned), and I resolve each below.

---

## 1. The resolved tension (calm ↔ colorful)

The false premise all six skills reject: that "calm" means low-contrast gray. It does not. The resolution every diagnosis lands on, stated once:

> **Calm = restraint in motion, copy, saturation, and density. Color, contrast, image, and scale are tools of *clarity*, not noise.** Hype comes from saturated fills, glow-on-everything, bright colored borders, bouncy/fast motion, exclamation, and many competing focal points. Immersion comes from one dominant image, real contrast, big type, and a single accent **that means something** (category = taxonomy, not mood).

Operating rules that keep "colorful" from tipping into "hyped":
- Color enters as **(a) real imagery, (b) brand logos, (c) category-tinted marks/fallbacks, and (d) one semantic accent per Thing** — never as a saturated card fill or a bright 1px colored border.
- **Chrome stays monochrome.** Nav, search, dividers, metadata, and the phone frame never take category color.
- **Gold (`#E8B25C`) is demoted from "the only color" to "the brand/wayfinding color"** — wordmark, lens pills, "Caught up," the "Kapyn-curated/you" signal. Content color comes from the 9-category spectrum.
- **One loud element per viewport.** Apple Today discipline: one oversized image-led feature, then quieter rows.

## 3. Surface & depth (resolved)

The page is **not** pure black. Warm it and add one elevation tier (this resolves "feels flat / co-planar," cited by all six):

```
Page canvas:    #0a0a0a   (keep; the warm grain overlay at opacity 0.035 stays)
Card surface:   #131210   (warm, raised — replaces the cold flat #111111)
Hairline:       rgba(255,255,255,0.07)   (white-alpha only — NEVER colored)
Inner highlight:inset 0 1px 0 rgba(255,255,255,0.07)   (top-edge light = "machined", not plastic)
```

- **Depth = one inset top-highlight + one corner glow, not heavy shadows.** Card recipe: surface `#131210` + hairline border + inner highlight + a corner radial `radial-gradient(120% 90% at 85% -10%, ${ring}33 0%, transparent 55%)`. Glow is *light*, not a fill — this is the calm way to add color and elevation simultaneously.
- **Concentric radii:** outer tile 18px, inner mark 11–13px. Marks use a crisp corner radius (`~0.28×size`), never `rounded-full`.

> **Disagreement flagged & call made:** one diagnosis wanted a full "double-bezel" outer-shell-wraps-inner-core treatment (the hero's `6px` shell) propagated to every body card. **Rejected for body cards** — at row/tile scale it adds nesting cost and visual heaviness that fights the "quiet field" goal. **Reserve the double-bezel for the hero and the one promoted "spotlight" card per section.** Body cards get the lighter recipe above (surface + hairline + inner highlight + corner glow). This keeps depth without making every one of ~40 rows a heavy object.

## 6. The keystone change (all six agree — do this first)

**Replace the gray `FaceMark` in `radar-shared.tsx`.** It renders ~40+ times per screen and is *the* texture the founder reacts to. One ~10-line edit recolors Today, Browse, and Toolkit at once. Resolved implementation: **logo if available, else category-tinted monogram/icon — never gray.**

```tsx
export function FaceMark({ face, category, logoUrl, size = 40 }: {
  face: Face; category?: string | null; logoUrl?: string | null; size?: number;
}) {
  const a = accentFor(category, face); // { fg, bg, ring }
  const Icon = FACE_ICON[face] ?? Sparkles;
  return (
    <span style={{
      flexShrink: 0, width: size, height: size, borderRadius: Math.round(size * 0.28),
      overflow: "hidden", background: a.bg, border: `1px solid ${a.ring}33`,
      boxShadow: "inset 0 1px 0 rgba(255,255,255,0.07)",
      display: "flex", alignItems: "center", justifyContent: "center",
    }}>
      {logoUrl
        ? <img src={logoUrl} alt="" style={{ width: "100%", height: "100%", objectFit: "cover" }} />
        : <Icon size={Math.round(size * 0.48)} color={a.fg} strokeWidth={1.9} />}
    </span>
  );
}
```

Also: `MetricChip` and `Eyebrow` take an optional accent and default to `accentFor(category)` — so an OSS chip reads orange, a model chip violet. Gold stays only for brand/you signals.

## 7. Motion principles (resolved — quiet is the brand guardrail)

The existing `radar-motion.ts` (`EASE = cubic-bezier(0.4,0,0.2,1)`, `DUR` palette, `useReducedMotion` branch, the `layoutId="lensPill"` spring) is **correct and must not be loosened** — that restraint is what stops "colorful" from becoming "hyped." Three layers, all in the Premium/Calm register:

1. **State feedback (the biggest current gap — there is none):** `whileTap={{ scale: 0.97 }}`, **130ms**, the signature ease, on every Row / tile / RailCard / lens pill / hero card. Cards shrink shadow on press. Desktop-only `whileHover={{ y: -2 }}`.
2. **Entry:** wire the existing variants to `whileInView` — fade-up `y: 12→0`, opacity `0→1`, **30–50ms stagger**, total under ~500ms, transform/opacity only (GPU-safe). Now the cascade lands on colorful tiles worth watching.
3. **Ambient (the missing third layer, kept tiny):** a single fixed-behind-content mesh glow tinted to the active lens hue (`radial-gradient(80% 50% at 50% -5%, ${lensHue}24 0%, transparent 60%)`, ≤0.14 alpha, `position: absolute` per the phone-column rule), crossfading ~320ms on lens switch.

> **Disagreements flagged & calls made:**

# Brand-coherence review: where calm-intelligence tips into hyped/cluttered, and the exact fixes

The grain of truth I'll concede up front: the keystone moves are correct and well-defended. FaceMark logo-else-tinted-monogram, the `accentFor` triad, the deterministic gradient fallback, "color from content not chrome," gold demoted to wayfinding, glow caps at `${ring}40`, `saturate(0.9)` — that is a coherent system, and it will read as calm-but-colorful if built as written. I verified the contrast spine: every `fg` (colorLabel) clears AA on both `#0a0a0a` (3.15–11.86, lowest is big-tech at 6.64) and `#131210`, while raw `colorAccent` lands at 3.15–6.21 — so the "never use raw accent as text" rule is real and load-bearing. Good.

But the brief says "resolve the tension, don't just say stay calm," and the specs have **not** fully resolved it. They've resolved it *per surface in isolation* and then quietly re-spent the calm budget six times over. The line gets crossed in five concrete places.

## 1. The "one loud object per fold" rule is asserted everywhere and violated structurally on Today

**Spec:** RADAR Today `colorStrategy` — *"One loud element (the hero) per viewport."* Then `layoutTopToBottom` stacks, in order: (3) HERO DECK at 210px with a peeking next card + gold pagination dots, then (4) SPOTLIGHT CARD — *"promoted to ONE full-width image card... the 'few things VERY prominent' move,"* double-bezel, ~190px — immediately below it.

**Risk:** A 210px double-bezel image deck and a ~190px double-bezel image spotlight are within ~400px of each other. On a 430px-wide phone, the second fold opens on a *second* full-bleed double-bezel hero. That is two loud objects per scroll, not one. "Double-bezel reserved for hero + the one promoted spotlight per section" (colorStrategy) literally licenses two bezels back-to-back. This is the exact mechanism by which Product Hunt's home feed reads busy: hero + featured + rail all shouting at 100% width. The rule isn't violated by accident — the layout *encodes* the violation.

**Fix:** Demote the spotlight's chrome, not its content. Keep SpotlightCard image-led and full-width, but **strip the double-bezel from it** — bezel is the hero deck's signature alone. Give the spotlight the light recipe (single hairline + one corner glow, no 6px outer shell). One *bezel* per viewport is the enforceable version of "one loud object." Alternatively, collapse the redundancy: if the hero deck already leads with the highest-signal Thing, the SpotlightCard is re-promoting the #2 — make the deck's first card *be* the spotlight and drop the separate section. Right now you're paying the hero tax twice for arguably the same editorial job.

# Feasibility & Data critique — what these specs assume Kapyn doesn't have, and what breaks at render

I read the actual code. Verdict up front: **the imageUrl story is real and cheap; the logo story is the load-bearing fantasy across all six surfaces.** Several specs treat `mcp__magic__logo_search` as a runtime data source. It is a build-time codegen tool. That single misread propagates into Today, Browse, Toolkit, Detail, and Content-Model. Below, per assumption: the specific spec line, the specific break, the specific fix.

## 1. `logoUrl` — the biggest unbacked assumption. There is no logo data and no runtime logo API.

**What the specs claim.** Every surface leans on a `logoUrl` field and names `mcp__magic__logo_search` as the populator. Content-Model: "LOGOS — logoUrl needs population at ingest via mcp__magic__logo_search + favicon fallback → new column radar_tools.logo_url." Toolkit: "Logo source priority: (1) mcp__magic__logo_search keyed off the tool name." Browse: "via mcp__magic__logo_search for named curated essentials." The component map's build order step 2 is literally "logo_search ingest pass to populate logoUrl."

**What's actually true (verified).** I loaded the tool schema. `mcp__magic__logo_search` returns **React component code (JSX/TSX/SVG) for a developer to paste**, from a curated brand library (its own examples are Discord/GitHub/Slack/Microsoft). It is invoked by a coding agent at authoring time. It is **not** an HTTP endpoint, it cannot run "at ingest" inside `/api/radar/tools`, and it returns a code string, not a `logoUrl`. Meanwhile `RadarThing` (radar-shared.tsx:38-51) has **no `logoUrl` field**, `SavedRadarTool` (storage.ts:44-52) has **no `logoUrl`**, and `radar_tools` has no `logo_url` column. So "populate logoUrl at ingest via logo_search" is not implementable as written.

**What breaks at render.** Nothing throws — but every "logo-led" claim silently collapses to the fallback. MCP servers are spec'd as "the single highest-color-yield kind because every MCP server borrows a famous brand logo" — that entire color thesis evaporates if logos aren't there. Worse: the spec routes the *fallback* through the favicon endpoint, which has its own failure modes (next point).

**The fix.**
- **Reclassify `logo_search` as a curation-time tool, not an ingest source.** Use it once, by hand, to generate logo components for the ~23 curated essentials + OSS canon (a known, finite, high-value set) and commit them to `/public` or as TSX. That is exactly what the tool is for and it's genuinely feasible.
- For the **open-ended** set (trending GitHub repos, PH launches, arbitrary entities) there is no logo source except favicons. Treat `logoUrl` as **derived at render from `url` host**, nullable, and make the **category-tinted monogram the default render path**, with the logo as an `onError`/`onLoad`-gated swap. The FaceMark rewrite already plans this — but every spec must stop describing logos as the *primary* and describe them as the *occasional enhancement on a curated subset*. The "color comes from logos" thesis must be downgraded to "color comes from category tint; logos are a bonus on ~30 known brands."

## 2. The Google favicon endpoint is the only runtime logo source — and it is low-quality and unreliable for exactly the entities that need it most.

**Spec line.** Repeated verbatim across Today/Browse/Toolkit/Detail/Content-Model: `https://www.google.com/s2/favicons?domain=<host>&sz=64` "keyed off the Thing's url." Detail's own risk section even admits it: "Google favicon at sz=64 is often a tiny 16px upscaled blob → looks worse than a clean monogram."

**Concrete breaks.**
- **No `url`, no favicon.** `entThing` sets `url: e.latestStory?.sourceUrl ?? null` (radar-map.ts:47). For an entity, that host is the **publisher of the news story** (techcrunch.com, theverge.com), **not the entity's own domain.** So a favicon keyed off a model entity's `url` renders *TechCrunch's* favicon next to "GPT-5." That is actively wrong provenance, not just low-res. The spec assumes `url` = the tool's homepage; for entities it is the article source.
- **`sz=64` lies.** Google returns whatever it has, frequently a 16×16 upscaled to 64 — blurry. For unknown hosts it returns a generic globe, which reads as "broken/generic," defeating the "never gray, never flat" goal.
- **Third-party request × ~40 marks/screen.** Browse/Toolkit render FaceMark "~40+ times." 40 cross-origin requests to google.com per scroll = latency, and a privacy/DPDP surface (the user's saved-tool hostnames leak to Google on every Toolkit open). Toolkit's own risk section flags DPDP but doesn't flag the favicon beacon.

**The fix.**
- **Entities: do not favicon off `url`.** Either resolve the entity's *canonical homepage* (needs a new `homepage` field on `entities` — a real new source, mark it as such) or **skip logos for entities entirely** and use the category monogram. The monogram is the honest default for entities; logos are for the curated tool set only.
- For the curated tool set, prefer the committed `logo_search` components (point 1) over favicons.
- If favicons are used at all, route them through a **same-origin proxy/cache** (`/api/favicon?domain=`) so you control sizing, caching, and don't beacon every saved hostname to Google — and so DPDP exposure is contained.

## 3. `imageUrl` — this one is real, cheap, and correctly diagnosed. Ship it. But two render traps remain.

**Verified TRUE.** `RadarItem.latestStory.imageUrl` exists (knowledge.ts:44, selected in `STORY_COLS`). `entThing` (radar-map.ts:38-52) genuinely **drops it** — there is no `imageUrl` on the returned object, and `RadarThing` has no field for it. `TrendingStory` already carries `imageUrl` (trending.ts:46). So "fetched then dropped, just plumb it" is accurate for Radar, and Trending already has it. This is the one data claim that fully holds.

**But two things still break at render:**
- **Coverage is low and the spec knows it but doesn't quantify the floor.** `news_items.image_url` is nullable; many rows are null. The Trending grid and Radar rails will be *mostly fallback gradients* on day one. That's acceptable *only if* the deterministic gradient is wired **before** any image path — and critically, branched on `imageUrl` falsiness up front, **not** relying on `<img onError>`. An empty-string or null `src` does **not** reliably fire `onError` in React; it can render a broken-image chrome icon or a 0×0 box. The CoverImage spec says "on error or empty src it swaps" — make sure the *empty* branch is a pre-render conditional, not an error handler.
- **Tools/essentials/canon have NO imageUrl at all, ever.** `toolThing`/`essThing`/`canonThing` (radar-map.ts:10-35) map from `RadarTool`, which has no image field in the table. So the spec's "spotlight/rails get real covers" is **only true for the entity subset.** Curated essentials — the on-ramp content — will be 100% gradient fallback. Browse's "Top Picks rail" mixing "freshest trending tool + curated flagships" will show gradient tiles for every curated flagship. Fine, but the design must not *assume* a photo there. Verify the gradient tile looks intentional as the *common* case for the tool half of the catalog.

**The fix.** Add `imageUrl?: string | null` to `RadarThing`; populate only in `entThing` (the others pass `null` honestly). Gate the gradient on `!imageUrl` as the *first* branch. Don't sell "image-led rails" for the curated/tool content — sell "logo-or-gradient tiles" there and reserve "image-led" language for entity-backed spotlights.

## 4. Detail's "Why it matters" / "Explain with Kapyn" assumes an API contract that doesn't exist and data passthrough that isn't wired.

**The fix.**

# Adversarial Review — Mobile & Focus Lens

I grounded every claim against the code. The triad, `FaceMark` gray (`#9a9a9a`), the dropped `imageUrl`, the gold-only `MetricChip`, the free-text `category`, and the thin essentials buckets (Media=1, Data/Agents/Eval=2) all check out. The specs are unusually well-reasoned — most "risks" sections pre-empt my obvious objections. So I'm going after what survives that pre-emption: the places where the spec contradicts its own focus discipline, where 430px math doesn't close, and where a "fix" is actually a feature in disguise.

---

## VERDICT BY SURFACE

### TRENDING — focused. Two real overload risks.

**1. The Top-3 stack + 2-up grid is two scan-densities stacked on one screen — and the spec never bounds the grid length.** Spec section (5) says "2-UP IMAGE TILE GRID … Replaces the dense text-row list" but gives no item cap. The old text list could run 20+ rows cheaply; 20 image tiles at 16:9 + 3-line text min-height is ~10 vertical screens of cover images on a 430px column. That's not a "calm vertical scan," it's an infinite-scroll gallery the spec elsewhere says it's avoiding.
- **Specific fix:** cap the grid at 8 tiles (4 rows) and make the "See all" affordance in section (4) load-bearing, not "Optional." Beyond ~8, covers stop being signal and become wallpaper. The honest trending signal lives in the Top-3; the grid is the tail.

**2. "Why it matters" appears on Top-3 AND every compact card AND is implied as the universal tap target — that dilutes the one genuine signal a busy builder wants.** Spec interactions: "Tap any card/tile → BreakdownSheet." But the spec also puts an explicit "Why it matters" link on the spotlight footer AND a "Why it matters" chevron on compact cards. If the whole tile opens the sheet, the inline link is a redundant second tap target competing for the same action — classic mobile thumb-confusion.
- **Specific fix:** Keep the inline "Why it matters" link ONLY on the spotlight (#1), where it's an editorial promise. On compact #2/#3 and grid tiles, drop the inline affordance entirely — whole-tile-tap opens the sheet. One target per object.

**3. Is Top-3/why-it-matters the signal a busy builder wants? Mostly yes, but the spec's own risk undercuts it.** The "N sources" heat chip is the honest "why it's trending" proof — but the spec admits (risks) that with a thin entity graph `sources` collapses to 0 and the chip "mostly won't render." So on a sparse day, Top-3 is just "3 recent stories with big images" — recency cosplaying as significance. That's the opposite of the signal a builder wants (they can get recency anywhere).
- **Specific fix:** When `sources < 2` across the board, the deterministic "why it leads" line (spec defers this to "optional") becomes mandatory, even if it only says "Freshest in {category}." Don't ship a "Trending" surface that silently degrades to "Recent" with no honesty marker. This flips the spec's "ship deterministic later" into "ship deterministic day one" — it's the contrastive signal, not a nice-to-have.

### RADAR Today — the most overloaded surface. Cut hard.

**1. Per-lens section ordering is THREE distinct information architectures maintained in one screen — that's a focus failure disguised as personalization.** Spec layout (5): Builder = 4 rails, Founder = spotlight+3, Exploring = 4 rails, each a different order. At 430px the user sees ~1.5 sections per fold. Three orderings means you're QA-ing and the user is learning three different scroll-maps of the same screen. The lens is supposed to *focus*; instead it triples the surface area.
- **Specific risk:** A builder who switches Builder→Founder→Builder gets a different scroll position and different leading hero each time — the screen feels unstable, not tailored.
- **Specific fix:** Lock the *section set and order* across lenses. Let the lens only re-rank *content within* rails and swap *which hero leads the deck*. Same spine, different fill. This is 1/3 the maintenance and gives the user one learnable map. The spec's own "calm" north star demands this.

**2. The hero deck is a horizontal scroll INSIDE a vertical scroll, and the spec stacks more horizontal rails below it.** Spec has: hero deck (horizontal), then "IMAGE-TILE RAIL" variants (horizontal), then "COLORED ROW LIST" (vertical). That's 2-4 horizontal scroll regions on a vertical-scroll phone. On mobile, nested-axis scrolling is the single most reliable way to make a thumb fight the UI — vertical-scroll intent gets eaten by a horizontal rail and vice versa.
- **Specific fix:** ONE horizontal element on Today — the hero deck. Convert the "image-tile rails" to either (a) a 2-up grid (vertical) or (b) "See all → Browse." The spec already routes "See all" to Browse; lean on it. Browse is where horizontal exploration belongs; Today is a vertical brief. The spec's "different shape so the eye gets rhythm" is aesthetics overriding thumb mechanics — reject it.

**3. The spec admits the closer card, the spotlight, AND each section header are all "the prominent move" — that's three "one loud things."** "SPOTLIGHT CARD … This is the 'few things VERY prominent' move" + hero deck "the one loud zone" + "one giant number per section." The whole point of "one loud object per fold" is one. The spec invokes the rule then violates it three times.
- **Specific fix:** Hero deck is the loud object. Demote the standalone SpotlightCard (section 4) — it's redundant with the hero deck which already leads with the highest-signal story. Two image-led heroes back-to-back (deck card #1 then spotlight) is a stutter, not a hierarchy. Cut the SpotlightCard from Today entirely; it survives on Browse and Detail where it isn't competing with a deck.

**4. 24px hero headline + 20px section titles + 17px item names + 15px body, all warm-white, on a 430px column = a screen with no quiet.** The spec promotes everything: section subs deleted, item titles 15→17px, body 14→15px, hero 21→24px. When every tier goes up, hierarchy *flattens* — the contrast that made 20px titles "punctuate" erodes because 17px items are right behind them. This is the dark text-wall problem re-created at a larger point size.
- **Specific fix:** Keep ONE size jump load-bearing (the 20px section title vs 15px body — that's your punctuation). Pull item titles back to 16px and let the FaceMark logo (not the type size) carry item prominence. The founder's "bigger fonts" directive is satisfied by the hero and section tiers; it does not require inflating every row.

### BROWSE — yes, it genuinely fixes the cannot-search-what-you-don't-know problem. One structural risk.

**The bento-leads-with-categories inversion is the correct fix** — leading with a search box over a flat list is exactly the "search for a tool you don't know exists" trap, and demoting search to a pill while leading with counted category tiles is right. This is the strongest spec of the set. But:

**1. The thin-bucket problem makes the bento lie about depth — and the spec's mitigation is half-committed.** Spec risk 3 offers two options ("merge thin buckets" OR "hide count<3"), then doesn't pick. A bento whose whole *raison d'être* is "live counts = proof of depth" cannot show a "Media 1" tile — that's anti-proof. And hiding count<3 tiles means Media/Agents/Eval/Data become *unreachable except by search* — re-creating the exact "can't find what you don't know" problem the surface exists to kill.
- **Specific fix — pick the merge, not the hide:** Merge thin buckets into "Build & ops" (Data & RAG + Eval + Agents) and keep Media folded into a broader tile. Hiding is the wrong call here precisely because of *this surface's own thesis*. Make the call in the spec; "either/or" ships as "neither" under deadline.

**2. The in-place FilteredCategoryView replaces sections 3-5 with no breadcrumb depth — on mobile, "where am I" gets lost fast.** Spec section (6): tapping a tile swaps the whole screen to a filtered view with a "‹ All categories" back row. That's one level, fine. But there's no indication this is a *different screen* vs a filter — and the back affordance is text-only top-left. On a 430px touch screen with no browser chrome (PWA), a text "‹ All categories" is a small, easily-missed target.
- **Specific fix:** Make the back affordance a real 36px circular button (match the Detail FloatingBackBar pattern for consistency), and keep the search pill visible in the filtered view so search is never more than one tap away regardless of depth. The spec hides search behind the curated front door — but once you're *inside* a category, search-within is the natural next move.

### TOOLKIT — focused and correctly scoped. One feature-in-disguise to cut.

**1. The ShareSheet's literal-text-preview pane is scope the surface doesn't need to carry, and it competes with the share action.** Spec section (5): "a preview of the exact text that will be shared (mono-ish … scrollable) so the user trusts what leaves the app." On a 58dvh sheet at 430px, a scrollable mono preview of a category share (up to 25 items) eats most of the sheet, pushing the actual channel buttons (the *point*) below the fold. You've made the trust-affordance louder than the action.
- **Specific fix:** For single-item share, show a one-line preview (it fits). For category share, show "Models — my Kapyn toolkit (7) + 6 more" as a *summary chip*, not the full scrollable text. The full text goes to WhatsApp/clipboard regardless; nobody proofreads a 25-line share sheet on a phone. Cut the scrollable preview pane — it's desktop-email thinking on a mobile share.

**2. "Spotlight tile when a category has exactly 1 item" adds a third tile component for an edge case.** Spec components: ToolkitTile AND SpotlightTile, the latter "used when a category has exactly one save." That's a whole heavier double-bezel variant to avoid a lone tile "looking lonely." On mobile this is over-engineering — a single 2-up tile with an empty second column is fine, or just render it full-width with the *same* ToolkitTile styling stretched.
- **Specific fix:** Cut SpotlightTile. A 1-item category renders one ToolkitTile at full column width — same component, `gridColumn: 1 / -1`. No new component, no "double-bezel for a lone save" rule to maintain. The lonely-tile problem is aesthetic anxiety, not a user problem.

### CONTENT-MODEL — the right idea, but it smuggles five integrations behind a "schema" framing.

**This is where focus discipline most needs to bite, because it's the surface most likely to balloon.**

**1. Eight kinds is a forward-looking schema; shipping seven *new content sources* (arXiv, MCP registry, agents, skills, OKF, logos) is a roadmap, not a surface.** The spec's own risk 2 admits "five separate integrations." The normalized `RadarThing` extension (the `kind` discriminator + `logoUrl`/`imageUrl`/`categorySlug`/`subtype`/`badges` fields) is genuinely cheap and correct. But the spec then specs PAPER cards, MCP cards, SKILL cards, AGENT cards in full visual detail — designing rooms for a house whose foundation (the sources) doesn't exist.
- **Specific fix:** Split this surface in two. Ship NOW: the type extension + FaceMark/accentFor keystone + the `imageUrl` plumbing (all zero-new-source). DEFER as separate specs gated on source availability: paper/mcp/skill/agent/okf card *designs*. Don't let the visual grammar for 5 unbuilt kinds bloat the PR that recolors the 2 kinds you have. The spec says "empty kinds just don't render" — good, so don't design them in this pass.

**2. SKILL as a top-level kind fails the focus test on its own merits — the spec admits it has "low individual signal."** Spec: skills "Render as a ROW … never a big spotlight (low individual signal)," "smallest, lowest-priority kind," "no public registry." A kind that can never be prominent, has no source, and the spec itself says is low-signal is not a kind — it's a row variant of tool at best.
- **Specific fix:** Cut SKILL from the kind enum entirely. If skills ever ship, they're `kind: "tool"` with a `subtype: "skill"`. Adding a top-level discriminator for content you have none of and that can never be loud is the definition of speculative complexity. Same logic puts OKF (the spec calls it "thin, mostly-evergreen") as a Browse-only `subtype`, not a hero-eligible kind.

**3. The kind→category color map means a builder scanning Today sees violet (model), blue (tool), violet (agent), teal (mcp), cyan (paper) all in one mixed rail — the rainbow the founder explicitly warned against.** Spec puts "Agents & MCP" rail (mixing violet + teal) and reuses category color as kind signal. Mixing 2 accents *within one rail* breaks the "color = taxonomy" promise (the rail isn't one taxonomy) and reintroduces visual noise.
- **Specific fix:** One accent per rail. If "Agents & MCP" must coexist, the rail header carries one accent (teal, "WIRE IT UP") and the *eyebrows* differentiate — but don't tint agent cards violet and mcp cards teal *in the same rail*. Either split into two rails or accept one rail color. The spec's per-kind color map is correct for Browse (where kinds are segregated into tiles) and wrong for a mixed Today rail.

## THE CROSS-CUTTING CUT

Every surface re-specs the same three foundations (FaceMark rewrite, accentFor, CoverImage fallback) and the same `imageUrl` plumbing. The component map already flags this ("build these once"). The risk is five surfaces each subtly diverging.

**Specific fix:** Make the `imageUrl` plumbing + FaceMark + accentFor + CoverImage a *single prerequisite PR* that all five surfaces depend on, with the triad mirrored in exactly one place (`accentFor` in `radar-shared.tsx`, importing from `categories.ts` — never re-declaring hexes). The specs say this; enforce it as a merge gate so no surface re-implements the gray-killer.

## WHAT I'D CUT, RANKED

1. **SKILL + OKF as top-level kinds** (Content-Model) → demote to `subtype`. Speculative, sourceless, low-signal.
2. **Per-lens section *reordering*** (Today) → lock the spine, re-rank within. Three IAs in one screen.
3. **Standalone SpotlightCard on Today** → redundant with the hero deck. Two heroes is a stutter.
4. **Horizontal image-tile rails on Today** → nested-axis scroll hell; route to Browse instead.
5. **ShareSheet scrollable text preview** (Toolkit) → summary chip; the full preview is desktop thinking.
6. **SpotlightTile** (Toolkit) → full-width ToolkitTile via `gridColumn`. No new component for a lone save.
7. **Inline "Why it matters" on compact/grid** (Trending) → whole-tile-tap is the one target. Keep inline only on #1.
8. **Designing 5 unbuilt kind-cards** (Content-Model) → ship the type + plumbing; defer the card designs to source-gated specs.

## WHAT GENUINELY EARNS ITS PLACE

- **Browse's bento-over-search inversion** — the single best decision across all six specs; it actually solves the stated discovery problem.
- **FaceMark rewrite + `imageUrl` plumbing** — correct, cheap, recolors four surfaces in one edit. Do it first.
- **Gold demotion to brand-only** + `fg`-for-text/`ring`-for-borders contrast discipline — the right resolution of calm↔colorful, and WCAG-honest.
- **Top-3 honest "N sources" heat chip** — the right signal *if* you make the deterministic fallback mandatory (my Trending fix #3), not optional.

**The through-line:** these specs over-trust the founder's "more, bigger, more prominent" directive and under-trust the 430px thumb. Every "few things very prominent" that becomes *several* things prominent, every per-lens/per-kind branch, and every nested horizontal scroll is the dark text-wall reincarnated as a colorful, busy wall. Cut to one loud object per fold, one scroll axis per screen, one IA per surface — and the colorful-but-calm target is actually reachable.
